# 历史架构与业务决策

本文合并早期 `architecture`、`business-process`、`rag-flow` 和 `phase1-scope`，只保留仍有解释价值的决策。

## 1. 产品定位

RagChunk 的早期定位是私有知识库 RAG：把组织文档转化为可检索知识，在用户提问时召回相关片段，再由大模型依据片段生成带引用的回答。

核心业务目标保持为：

- 知识沉淀：文档可以解析、切片、索引和更新。
- 有据问答：答案必须以检索片段为依据，无证据时拒答。
- 可追溯：回答关联文档和切片，便于核对。
- 可运营：管理员能够处理失败、验证召回并持续调优。

## 2. 历史流程模型

```text
离线建库：创建知识库 → 上传 → 解析规范化 → 切片 → 向量化 → 入库
在线问答：接收问题 → 查询向量化 → 检索过滤 → 上下文组装 → 生成回答
运营闭环：问题反馈 → 召回分析 → 文档/参数调整 → 重新处理
```

早期将业务活动划分为三类：

| 类别 | 主要活动 |
|---|---|
| KB | 创建知识库、配置、上传、解析、切片、向量化、质量检查 |
| QA | 接收问题、检索、过滤、增强、生成、引用和反馈 |
| OP | 文档新增、更新、下线、召回测试和参数调优 |

这一划分仍适合作为领域边界，但具体状态、API 和模块以当前实现为准。

## 3. 一期取舍

一期选择了较小闭环：

- 支持 TXT、Markdown、DOCX，后续又增加 Excel；不包含 PDF/OCR。
- 采用规则切片主路径，并保留按需 AI 语义重切。
- 只做单层 Chunk，不做父子分块。
- 使用 Embedding + pgvector，不做关键词倒排和 Rerank。
- 采用本地对象存储归档和应用内异步处理。
- 保留 `inmemory` 模式用于开发验证。

这组取舍解释了当前系统为什么能快速形成完整闭环，也解释了后续在可靠任务、混合检索、权限和评测方面的缺口。

## 4. 长期不变量

- 同一知识库入库和查询必须使用兼容的 Embedding 模型与维度。
- 切片或 Embedding 配置变化通常意味着重新建立索引。
- 生成模型不能替代检索，检索结果不足时不得编造业务事实。
- 原始文档、处理状态、Chunk 和索引需要可追溯。
- 文档下线或权限撤销后，不应继续出现在检索结果中。

## 5. 历史状态模型

早期使用 `PROCESSING / SUCCESS / FAILED` 三态，随后扩展为异步处理阶段：

```text
QUEUED → OSS_ARCHIVING → PARSING → CHUNKING → EMBEDDING → SUCCESS / FAILED
```

该模型适合 MVP 展示，但进程内任务、失败恢复和索引原子切换仍属于后续生产化内容。

## 6. 已废弃或尚未实现的设想

以下内容曾出现在早期文档中，但不能视为当前能力：

- PDF、网页、Notion 等数据源。
- 父子分块、经济索引和多模态索引。
- 完整关键词/向量混合检索和 Rerank。
- 文档级权限、多租户、计费和完整运营闭环。
- 多种 AI 切片任务叠加执行。

对应演进顺序见 [生产级演化方案](../architecture/生产级演化方案.md)。
