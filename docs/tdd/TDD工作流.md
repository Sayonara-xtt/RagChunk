# RagChunk 版本门禁与 TDD 工作流

本流程用于 RagChunk 的版本需求、设计、测试、实现和验收。核心规则是：**需求先审，设计与测试再审，批准后才编码；实现阶段一个行为、一个有效 RED、一个最小 GREEN。**

## 1. 适用范围

- 按生产级演化路线执行的每个版本；
- 新业务能力、缺陷修复和可观察行为变化；
- 架构、数据、配置、安全、异步、模型或外部边界调整；
- 纯文档整理可不走代码 TDD，但仍须明确范围并保留用户已有修改。

每个版本使用独立目录：

```text
docs/versions/Vx.x/
├── README.md
├── 01-需求单.md
├── 02-详细设计.md
├── 03-测试用例设计.md
└── 04-实施与验收报告.md
```

复制模板时不得删除状态、风险等级、审核记录和变更记录字段。

## 2. 风险分级

风险等级只控制文档深度，不允许省略需求单、详细设计或测试用例设计。

| 等级 | 适用变化 | 文档和验证要求 |
|---|---|---|
| L1 | 内部重构、小型缺陷、无外部契约变化 | 三份精简前置文档；说明为何无外部行为变化及回归范围 |
| L2 | 新功能、API、持久化、异步流程或外部集成 | 三份完整前置文档；覆盖兼容、异常、集成和回归 |
| L3 | 权限、安全、数据迁移、删除、并发、不可逆操作 | L2 要求，加数据/安全风险、备份或回滚方案和人工验收清单 |

风险不明确时按较高等级执行。降级必须在需求单记录理由并由开发者批准。

## 3. 两道人工审核门禁

### 门禁 A：需求审核

AI 先生成 `01-需求单.md`，状态设为 `待审核`，然后停止版本推进。只有开发者明确批准后，状态才能改为 `已批准`，并开始详细设计和测试用例设计。

需求单至少包含：

- 业务背景、版本目标、范围和不包含项；
- `REQ-*` 需求编号和可观察验收标准；
- 兼容性、性能、安全、数据与运维约束；
- 风险等级、依赖、假设和待决问题。

### 门禁 B：设计与测试审核

需求批准后生成 `02-详细设计.md` 和 `03-测试用例设计.md`，状态设为 `待审核`，再次停止版本推进。只有两份文档均被开发者明确批准，才能：

- 新增或修改测试代码；
- 修改生产代码、配置、迁移或运行脚本；
- 执行会改变外部系统或数据库状态的实施操作。

AI 不得自行批准、从沉默推断批准，或把“继续分析”“看看代码”等指令视为批准实施。开发者明确表达“批准”“按设计实施”或等价含义后才算通过。

## 4. 追踪关系与文档状态

编号格式：

```text
REQ-V09-001     需求
DES-V09-001     设计项
UT-V09-001      单元测试
IT-V09-001      集成测试
CT-V09-001      契约测试
E2E-V09-001     端到端测试
```

每条测试用例必须关联至少一个需求编号和设计项编号。实施后在验收报告补充自动化测试类/方法与证据文件，形成：

```text
REQ → DES → UT/IT/CT/E2E → 测试方法 → 证据
```

文档状态只允许：`草稿`、`待审核`、`已批准`、`实施中`、`已完成`。审核人和审核时间必须由真实审核结果填写，不得使用 AI 作为审核人。

## 5. 开发准入（DoR）

进入测试代码或生产代码修改前，必须同时满足：

- 门禁 A、门禁 B 均通过；
- 每条目标行为已有 Given / When / Then；
- 正常、边界和失败场景已列出；
- Mock 边界、测试数据与关键断言已明确；
- 允许和禁止修改的范围已明确；
- 聚焦、单元、集成及必要 E2E 命令已明确；
- API、数据、配置、异步、外部模型、回滚影响已评估；
- 高风险操作已经取得额外人工确认。

### 5.1 图示适用性检查

L2/L3 详细设计在门禁 B 前必须逐项判断：组件关系用 `flowchart`，依赖步骤和异步交互用 `sequenceDiagram`，状态迁移用 `stateDiagram-v2`，多表关系用 `erDiagram`。适用时使用标准 Mermaid，不适用时记录理由；单图单主题、中文命名清晰、节点建议不超过 12 个。图示只摘要关系，接口、异常、安全、兼容和回滚仍由正文与表格定义。

任一条件不满足时只完善文档，不进入编码。

## 6. TDD 微循环

每次只从已批准的 `03-测试用例设计.md` 选择一个最小行为。

### RED

1. 新增当前用例所需的最小测试代码。
2. 执行聚焦测试并将日志写入 `docs/tdd/evidence/`。
3. 确认失败来自目标行为缺失，而不是编译、环境或测试数据。
4. 第一次就是绿色时，检查行为是否已经存在或断言是否无效。

```powershell
.\scripts\tdd-test.ps1 -Mode focus -Test RuleChunkerTest#行为名称 -Phase RED
```

### GREEN

只实现使当前失败测试通过的最小生产代码，不顺手加入未批准行为。

```powershell
.\scripts\tdd-test.ps1 -Mode focus -Test RuleChunkerTest#行为名称 -Phase GREEN
.\scripts\tdd-test.ps1 -Mode unit -Phase REGRESSION
```

### REFACTOR

相关测试绿色后，每次只做一种结构调整，调整后立即运行聚焦测试和单元回归。发现新行为时先回到文档和审核门禁，不在重构阶段偷偷实现。

## 7. 测试分层

| 层级 | JUnit 标签/入口 | 职责 |
|---|---|---|
| 单元测试 | `@Tag("unit")` | 切片规则、校验、不变量、配置合并、问答编排 |
| 集成测试 | `@Tag("integration")` | Spring 上下文、PostgreSQL/pgvector、文件与存储适配 |
| 契约测试 | integration 中的 MockMvc 等 | HTTP 状态、字段、错误结构和兼容性 |
| E2E | `scripts/test-e2e.ps1` | 创建库、异步上传、轮询、切片查询、问答 |

测试用例设计记录场景、输入、断言和风险，不复制测试实现。验收报告链接到真实测试类和方法。

## 8. 标准验证与证据

```powershell
# 快速单元回归
.\scripts\tdd-test.ps1 -Mode unit -Phase REGRESSION

# 不启用外部数据库的集成检查
.\scripts\tdd-test.ps1 -Mode integration -Phase REGRESSION

# Docker + Testcontainers PostgreSQL/pgvector
.\scripts\tdd-test.ps1 -Mode integration -WithPostgres -Phase REGRESSION

# 全量测试
.\scripts\tdd-test.ps1 -Mode all -Phase REGRESSION
```

每次执行在 `docs/tdd/evidence/` 生成日志。该目录不提交 Git，也不会被 Maven `clean` 删除；CI 上传日志作为构建产物。`04-实施与验收报告.md` 只记录证据文件名、命令和结论。

## 9. 审核后变更控制

已批准版本出现以下变化时，必须停止编码：

- 新增或删除需求；
- 修改 API、数据库、配置格式、权限或安全边界；
- 改变验收标准、测试层级或关键断言；
- 引入新的外部依赖、迁移、数据删除或不可逆操作；
- 实施发现设计无法成立，需要扩大范围。

处理顺序：更新需求/设计/测试文档 → 标记受影响编号 → 补充变更记录 → 重新通过对应门禁 → 恢复 TDD。

## 10. 过渡测试门禁

在已知基线清零前：

1. 当前聚焦测试必须经历有效 RED 并最终 GREEN；
2. `unit` 标签测试必须全部通过；
3. 受影响集成测试必须实际执行并记录结果；
4. 完整回归不得增加基线外失败；
5. 不得通过 `@Disabled`、删除断言、扩大容差或盲目重试隐藏失败。

具体基线见 [已知基线](已知基线.md)。

## 11. 版本完成定义（DoD）

- 所有批准的 `REQ-*` 均有设计和测试覆盖；
- 每个新增行为都有自动测试并观察到有效 RED；
- 聚焦、单元和受影响回归均有真实证据；
- 没有删除、跳过或弱化关键测试；
- API、配置、迁移和业务文档同步；
- 设计偏差、假设、基线差异和剩余风险已记录；
- L3 版本完成备份/回滚和人工验收检查；
- `04-实施与验收报告.md` 状态为 `已完成`；
- 版本结束后停止，等待开发者发出下一版本指令。
