## 1. 背景与问题

RagChunk 当前已经形成可运行的经典 RAG 主链路：创建知识库、异步上传、文档解析、规则与 AI 混合切片、向量化入库、检索问答和引用返回。项目同时具备以下自身优势：

1. 基于 Spring Boot、Java、PostgreSQL 和 pgvector，便于接入既有 Java 企业系统；
2. 采用“规则切片 → 质量评估 → 按需 AI 重切 → 校验失败回退”的可控混合切片策略；
3. 已建立流式原件归档、异步处理阶段、模型与存储适配边界；
4. 已建立版本门禁、测试分层、TDD 和证据留存机制。

RAGFlow 可作为专业 RAG/企业上下文引擎的能力参考，其可借鉴优势主要包括：

1. 面向 PDF、扫描件、表格、图片和复杂版面的深度文档理解；
2. 可解释、可检查、可人工干预的 Chunk 生产过程；
3. 关键词与向量混合召回、RRF/重排、元数据过滤和检索调试；
4. 有据作答、引用定位和端到端质量评测；
5. 数据源同步、知识生命周期管理及面向上层应用的标准服务接口；
6. 在基础 RAG 稳定后逐步发展多知识库路由、GraphRAG、RAPTOR 和 Agentic RAG。

当前总体演化路线已经覆盖评测、可靠摄取、检索、权限、数据源和运维，但仍存在以下问题：

- 缺少明确的产品边界，容易同时向专业 RAG 引擎和通用低代码 AI 平台扩张；
- 缺少独立的“复杂文档理解与可解释切片”演进阶段；
- 质量评测、摄取可靠性、文档理解和检索质量之间的依赖关系表达不够清晰；
- 各版本缺少统一的业务结果、进入条件、退出条件和风险说明；
- GraphRAG、Agent、分布式服务等高级能力缺少启动前置指标，存在过早复杂化风险；
- 当前功能状态、总体演化方案和后续版本目录可能随着实施产生版本口径漂移。

因此，V0.9 需要同时建立问答质量证据基线，并将后续路线重整为“RAG 核心能力优先、企业治理随后、平台能力最后”的单一演化主线。

## 2. 产品定位与演化原则

### 2.1 产品定位

RagChunk 定位为：

> 面向 Java 企业技术栈的、可评测、可恢复、可治理、可集成的企业文档 RAG 核心服务。

RagChunk 负责文档摄取、解析、切片、索引、检索、引用、质量评测、权限过滤和知识生命周期；上层门户、通用工作流画布、业务应用市场可以通过标准 API、Tool 或 MCP 等方式集成，不在近期核心范围内重复建设。

技术架构坚持“**Java/Spring 主系统＋可选 Python 能力服务**”：

- Java/Spring 主系统是业务控制面和唯一事实来源，持有 API、任务状态、文档与索引版本、Chunk 元数据、权限、审计、检索编排、质量记录和降级决策；
- Python 能力服务是可选、可替换、可独立部署的专业能力面，仅承载 OCR、版面分析、表格恢复、多模态文档理解、本地模型推理、Rerank 或实验性检索算法；
- Python 能力不得直接成为知识库、文档、Chunk、索引或权限数据的第二事实来源；
- Python 能力不可用、超时或结果校验失败时，Java 主系统必须能够按已批准策略回退、降级或明确失败；
- 不需要 Python 专业能力的部署场景，RagChunk 必须保持纯 Java 主链路可运行。

### 2.2 演化原则

1. **先证据后优化**：没有标准问题集和基线指标，不开展不可量化的检索算法升级；
2. **先可靠后丰富**：先保证任务可恢复、索引可回滚，再增加文件类型和数据源；
3. **先文档后检索**：先保证解析与 Chunk 输入质量，再叠加混合召回和重排；
4. **权限前置到检索层**：企业权限必须在召回阶段生效，不能只做页面或接口入口控制；
5. **保留可解释回退**：AI 解析、AI 切片、Rerank 和高级检索不可用时必须有确定性降级路径；
6. **保持模块化单体**：没有容量、隔离或独立发布证据，不提前拆分微服务；
7. **核心服务优先**：不以复制通用低代码 AI 平台为目标，上层应用通过开放契约集成；
8. **多语言但单一事实源**：允许通过稳定契约使用 Python AI 生态，但核心业务状态、权限与生命周期始终由 Java 主系统管理；
9. **能力服务可选可替换**：Python 能力必须具备版本标识、能力声明、超时、幂等、校验、观测和替换边界，禁止在领域代码中散落 Python 实现细节；
10. **高级能力指标驱动**：GraphRAG、多跳检索和 Agentic RAG 只有在标准集证明经典 RAG 无法满足目标时才进入版本范围。

## 3. 版本目标

V0.9 的目标是建立可复现的问答运行追踪与质量评测基线，并产出唯一、无冲突、具备依赖和门禁关系的生产级演化路线，使后续文档理解、检索优化和企业治理都能够以真实质量证据为依据实施。

可观察结果包括：

- 每次问答具有唯一运行标识和可查询的输入、检索、引用、模型、耗时及结果快照；
- 可以定义和重复执行标准问题集，并产出检索与回答质量指标；
- 可以比较两组模型、Prompt、切片或检索配置的效果；
- 项目文档中只有一份规范性生产级路线，其他文档引用该路线而不复制冲突内容；
- 后续版本按质量基线、可靠摄取、文档理解、检索质量、企业治理、数据生命周期、生产运营、上下文平台的依赖顺序推进。

## 4. 范围

### 4.1 包含

- 明确 RagChunk 产品定位、核心职责、上层集成边界和不建设边界；
- 建立 RagChunk 自身优势与 RAGFlow 参考能力的映射矩阵；
- 明确 Java/Spring 主系统与可选 Python 能力服务的长期职责边界、事实源、调用原则和失败降级要求；
- 重整并统一后续版本编号、主题、业务结果、依赖、风险等级和完成门禁；
- 为每次问答生成并返回唯一 `runId`；
- 保存问答运行状态、耗时、模型及 Prompt 版本、检索命中、引用、答案和异常摘要；
- 提供知识库维度的问答运行列表和详情管理契约；
- 支持标准问题集、标准答案、必须命中文档和应拒答标记；
- 支持重复执行评测并保存执行配置快照；
- 计算至少包括 Recall@K、MRR、正确性、忠实度和引用准确率的质量结果；
- 支持两次评测运行的结果比较；
- 同步规范性架构路线、项目进度、文档索引和后续版本入口，但不伪造尚未实现能力。

### 4.2 不包含

- 本版本不实现 PDF/OCR、版面分析、表格结构恢复等复杂文档解析；
- 本版本不实现关键词倒排、RRF、Reranker、父子 Chunk、GraphRAG 或 RAPTOR；
- 本版本不实现租户、用户、角色、文档 ACL、SSO 或审计后台；
- 本版本不实现外部数据源连接器、增量同步或删除传播；
- 本版本不实现通用低代码工作流画布、模型市场、插件市场或完整 Agent 平台；
- 本版本不创建或部署 Python 能力服务，不引入 Python 运行时，也不改变当前纯 Java 主链路；
- 本版本不拆分微服务，不引入分布式 Worker；
- 本版本不改变现有问答 API 的主要业务语义；若增加 `runId` 等字段，必须保持向后兼容；
- 本版本不以单次人工问答成功代替标准问题集质量验收。

## 5. 重整后的演化路线

以下路线在门禁 A 批准后进入详细设计，并作为后续规范性版本主线。每个未来版本仍须建立独立需求、设计、测试和验收文档，并单独通过人工门禁。

| 版本 | 主题 | 主要业务结果 | 参考优势 | 预计风险 |
|---|---|---|---|---|
| V0.9 | 质量基线与问答可追踪 | 问答过程可复盘，模型、Prompt、切片和检索效果可比较 | RagChunk TDD/证据治理；RAGFlow 检索测试与引用 | L2 |
| V1.0 | 可靠摄取与索引版本 | 服务重启可恢复，重复任务不重复入库，失败重建不影响在线索引 | RagChunk 异步阶段与适配边界；RAGFlow 摄取流水线 | L3 |
| V1.1 | 文档理解与可解释切片 | 支持 PDF/OCR/版面和表格等优先格式，Chunk 可检查、可修订、可追溯；按收益决定是否接入首个可选 Python 文档能力服务 | RagChunk 混合切片与失败回退；RAGFlow 深度解析；Python 文档 AI 生态 | L2 |
| V1.2 | 混合检索与引用可信 | 关键词和向量并行召回、融合、过滤、重排、父子上下文及检索调试；Rerank 可由 Java 适配器调用外部或 Python 能力服务 | RAGFlow 混合检索、重排、元数据过滤和引用 | L2 |
| V1.3 | 企业权限与审计 | 租户隔离、知识库成员、文档 ACL、撤权生效及完整审计 | RagChunk Java 企业集成；企业级知识权限实践 | L3 |
| V1.4 | 数据源与知识生命周期 | 数据源增量同步、版本变化、删除和撤权可以传播到有效索引 | RAGFlow 数据连接与摄取管道 | L3 |
| V1.5 | 生产运营与成本治理 | 指标、告警、限流、配额、熔断、备份恢复、灰度与成本可见 | RagChunk 工程治理；生产级 RAG 运维实践 | L3 |
| V2.0 | 企业上下文服务平台 | 标准 Retrieval/Context API、Tool/MCP、多知识库路由和受控 Agentic RAG | RAGFlow 上下文层与 Agentic RAG | L2/L3，按最终范围确定 |
| V2.5 | 条件式规模化 | 仅在容量指标证明需要时拆分 Worker、搜索服务或采用分布式调度 | RagChunk 模块化单体演进原则 | L3 |

### 5.1 阶段关系

```text
质量证据 V0.9
  → 可靠摄取 V1.0
  → 文档理解 V1.1
  → 混合检索 V1.2
  → 企业权限 V1.3
  → 数据生命周期 V1.4
  → 生产运营 V1.5
  → 上下文平台 V2.0
  → 指标驱动规模化 V2.5
```

### 5.2 高级能力启动条件

GraphRAG、多跳检索、表格专用检索和 Agentic RAG 不预先承诺进入某个小版本。至少满足以下条件后，才允许更新相应版本需求：

- 已存在稳定、可重复执行的标准问题集；
- 经典混合检索和 Reranker 已完成调优；
- 失败问题能够明确归因为关系推理、多跳检索或工具执行不足；
- 新方案具备明确的质量收益目标、延迟预算、成本预算和降级方案；
- 已通过对应版本的人工范围审核。

### 5.3 Java 主系统与 Python 能力服务规划

```text
上层业务 / Dify / 企业门户
            |
      API / Tool / MCP
            v
+----------------------------------------------+
|          RagChunk Java/Spring 主系统          |
| API、任务、事务、版本、权限、审计、检索编排   |
| Chunk 校验、引用、评测、重试、降级、事实数据   |
+----------------------+-----------------------+
                       | 稳定能力契约
                       | jobId / objectUri / hash
                       | parserVersion / traceId
                       v
          +-------------------------------+
          | 可选 Python 专业能力服务       |
          | OCR、版面、表格、多模态        |
          | 本地模型、Rerank、实验算法     |
          +-------------------------------+
```

| 能力或数据 | Java/Spring 主系统 | 可选 Python 能力服务 |
|---|---|---|
| 对外 API、Dify/门户集成 | 负责 | 不直接暴露业务主契约 |
| 知识库、文档、Chunk 元数据 | 唯一事实来源 | 只接收任务输入并返回候选结果 |
| 任务状态、幂等、重试、版本切换 | 负责 | 遵守任务契约，不独立改变业务状态 |
| 权限、租户、ACL、审计 | 负责并在检索阶段强制执行 | 不独立作授权决定 |
| 规则切片、质量校验、失败回退 | 负责 | 可返回 AI 解析或重切候选结果 |
| OCR、版面、表格、多模态 | 提供适配器和降级路径 | 按版本选择性实现 |
| Embedding、Rerank、实验算法 | 负责编排、版本快照和质量验收 | 可作为一种可替换执行后端 |
| 结果持久化和索引激活 | 负责 | 不直接激活生产索引 |

能力服务契约至少应考虑：任务 ID、文档版本 ID、对象地址、内容哈希、能力名称与版本、模型版本、Trace ID、幂等键、超时、结果清单、页码/坐标/层级等来源信息、置信度及结构化错误。具体使用 HTTP、gRPC、消息队列或对象存储清单，由引入首个 Python 能力服务的版本单独设计和审核。

## 7. 非功能约束

| 类型 | 约束或指标 |
|---|---|
| 兼容性 | 现有知识库、上传、Chunk 查询和问答主要契约保持兼容；新增 `runId` 等字段不得要求旧客户端同步升级；未来 Python 能力通过适配器接入，不向领域层泄漏实现协议 |
| 性能与容量 | 追踪写入不得无上限阻塞问答主链；评测采用异步任务；详细指标、超时和容量在详细设计中基于现有基线确定 |
| 安全与权限 | Prompt、原文片段、答案和异常可能包含敏感数据；管理查询不得新增匿名访问面，并为 V1.3 文档 ACL 预留主体和租户字段；未来 Python 能力服务按最小权限访问对象，凭据不得进入任务载荷、日志或结果清单 |
| 数据一致性 | 运行记录、检索轮次、引用和评测结果必须能关联同一快照；部分记录失败需有明确状态，不得伪装为完整成功 |
| 可观测性 | 记录追踪写入失败、评测阶段、耗时和无法评分原因；日志不得输出密钥或不必要的完整敏感正文；未来跨语言调用必须贯通 Trace ID，并记录能力与模型版本、延迟、超时、降级和错误分类 |
| 运维与部署 | 数据库迁移必须可验证并具备回滚或前向修复说明；不得要求本版本拆分新微服务；未来 Python 服务必须是可选部署单元，未配置时主系统健康状态和纯 Java 能力不受影响 |
| 可测试性 | 新行为遵循 TDD；外部 LLM、Embedding 只在真实边界 Mock；质量指标纯逻辑使用单元测试，持久化/API/异步流程使用集成与契约测试 |
| 文档一致性 | `docs/architecture/生产级演化方案.md` 作为规范性路线；README、开发进度和版本索引只摘要并链接，不维护冲突副本 |

## 8. 依赖、假设与待决问题

### 8.1 依赖

- V0.8 工程治理基线已经完成；
- 当前问答、检索、引用和模型适配接口可作为追踪采集边界；
- PostgreSQL/Flyway 可承载运行追踪和评测元数据；
- 现有测试脚本继续作为 RED/GREEN 和回归证据入口。

### 8.2 假设

- V0.9 优先解决单实例、单体架构下的质量可见性，不以分布式评测为目标；
- 自动正确性和忠实度评分允许使用可替换 Judge，但 Judge 结果必须与确定性检索指标分开呈现；
- 路线借鉴 RAGFlow 的能力目标和产品经验，不要求复制其语言、组件、数据库或内部实现；
- Python 只作为专业 AI 能力的可选执行环境，不替代 Java/Spring 主系统，不拥有生产索引激活权；
- 后续上层应用优先通过 API、Tool 或 MCP 集成，不在近期建设通用工作流画布。

### 8.3 待决问题

以下问题必须由开发者在门禁 A 审核时确认，或授权在详细设计中形成明确方案：

1. V0.9 是否同时交付最小管理页面，还是仅交付管理 API 和可验证结果；
2. 问答正文、命中 Chunk 和 Prompt 快照保存完整内容，还是采用引用 ID、脱敏摘要和可配置保留策略；
3. 正确性与忠实度 Judge 默认使用现有千问适配器、Ollama，还是只定义可替换接口；
4. 评测任务是否复用当前异步执行设施，还是建立数据库持久化任务；后者与 V1.0 的边界需要避免重复；
5. V1.1 第一批复杂文档格式的优先级，是 PDF 优先，还是 PDF 与图片 OCR 同时进入；
6. V2.0 对 Dify 等上层平台的首个集成契约，优先选择外部知识库 API、Tool 还是 MCP。
7. 首个 Python 能力服务采用同步 HTTP/gRPC、异步消息任务还是对象存储结果清单，由 V1.1 根据文件大小、超时和恢复要求确定；
8. Python 能力服务是项目自建、封装第三方开源解析器，还是仅对接外部托管能力，需要在 V1.1 范围审核时明确许可证、数据出域和运维责任。

## 9. 风险分级依据

本版本定为 **L2**，原因如下：

- 将新增问答运行与评测相关持久化数据；
- 将新增或扩展管理 API，并以兼容方式扩展问答响应；
- 将引入异步评测流程及外部 Judge 边界；
- 路线文档调整本身不改变生产行为，但 V0.9 的实际业务能力属于新 API、持久化和异步流程调整。

本版本不涉及权限模型实施、数据删除、不可逆迁移或跨租户隔离，因此当前不定为 L3。若详细设计引入删除策略、自动清理、租户隔离、安全权限或不可逆迁移，必须升级为 L3 并重新通过门禁 A。
